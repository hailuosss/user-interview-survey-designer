# 用户访谈问卷设计 Skill

面向 UI/UX 与产品设计师，辅助 AI 将研究目标转化为用户访谈提纲、调研问卷或招募筛选题，并在交付前检查问题质量。

本项目是一套供 AI 读取的 Markdown 指令，不是独立运行的软件。核心文件无需编译或部署；生成质量取决于所使用的 AI、研究输入和后续人工复核。

## 可以做什么

| 任务 | 主要产出 |
| --- | --- |
| 设计用户访谈 | 开场、暖场、核心问题、可选追问、人群分支、时间安排、必问标记和结束问题 |
| 设计调研问卷 | 填写说明、题型、选项、量表、展示条件与跳题逻辑 |
| 设计招募筛选题 | 围绕研究对象和实际经历的筛选问题 |
| 审查已有问题 | 诱导性、复合问题、经历适配、选项和跳题检查，以及实际修改记录 |
| 联合交付 | 共享研究目标、分别设计的访谈提纲与问卷，附研究者说明 |

适用于了解用户行为、需求、产品使用体验，以及准备现有页面或原型的评估。不是招聘面试工具，也不用于生成虚构的用户回答或研究结论。

## 文件结构

```text
user-interview-survey-designer/
├── README.md                 项目介绍与使用方法
├── SKILL.md                  AI 的入口指令和共同流程
└── references/
    ├── interview.md          访谈设计规则
    └── survey.md             问卷与筛选题设计规则
```

- [SKILL.md](SKILL.md)：判断任务、检查输入、建立研究映射、审查问题并交付。
- [访谈设计规则](references/interview.md)：规定时间预算、追问、分支、页面任务与主持人说明。
- [问卷设计规则](references/survey.md)：规定题型、选项、量表、跳题、提示效应和分析口径。

三个核心文件需要一起保留。当前不依赖执行脚本、产品数据库或外部连接器。

## 快速开始

### 在能读取本地文件的 AI 工具中使用

1. 下载并解压项目，保留目录结构。
2. 将项目放入 AI 能访问的工作目录。
3. 明确要求 AI 读取 `SKILL.md`，并按任务读取它引用的规则文件。
4. 提供研究背景；若 AI 发现关键缺口，补充后再生成材料。

可以从下面这段指令开始：

```text
请读取 user-interview-survey-designer/SKILL.md，
并按当前任务读取其引用的规则文件。

我需要：[访谈提纲 / 调研问卷 / 招募筛选题 / 联合交付 / 审查已有问题]。
产品与场景：
研究目标及希望支持的决策：
受访者类型与样本计划：
已有事实与待验证假设：
访谈形式、时长及是否查看页面：
问卷用途与目标填写时长：
需要的语言和输出格式：

先检查输入，集中询问关键缺口，不重复询问已经提供的信息。
不要编造产品规则，不预设问题一定存在。
请分开输出受访者材料与研究者说明，并附审查和实际修改记录。
```

只需填写与当前任务相关的项。无需每次同时生成访谈和问卷。

### 其他使用方式

如果工具支持本地 Skill，可按该工具的安装说明导入整个技能目录；不同工具的安装位置和调用方式可能不同。本项目尚未逐一验证各工具的安装兼容性。

如果聊天工具不能读取文件夹，可以先提供 `SKILL.md`，再提供本次任务需要的规则文件正文。不要假定只发送 GitHub 链接就一定会读取全部内容。

## 需要提供哪些信息

| 输入 | 示例或说明 |
| --- | --- |
| 研究背景 | 产品、使用场景、当前关注的问题 |
| 研究目标 | 想了解什么，研究将支持什么决定 |
| 研究对象 | 用户类型、筛选条件、招募方式与样本计划 |
| 已有线索 | 用户反馈、数据或产品自查；标明哪些只是猜测 |
| 执行条件 | 访谈形式、时长、录音、屏幕共享、页面或原型 |
| 问卷要求 | 用于筛选、访谈前背景收集，还是独立调研 |
| 交付要求 | 语言、格式、交付范围 |

关键输入不足时，Skill 要求 AI 集中澄清；非关键缺口可以用明确标注、可调整的假设处理。

## 工作流程

1. **检查研究输入**：区分已知事实、待验证假设和未知信息。
2. **建立问题框架**：把研究目标对应到所需证据、适用人群和具体问题。
3. **分别设计材料**：访谈关注具体经历与追问；问卷关注题型、选项与跳题。
4. **审查并修订**：检查每题的中立性、单一重点和适用条件，同时检查时间与逻辑。
5. **交付并标明状态**：区分已完成的文字审查与尚待实施的试访或预测试。

联合设计时还会检查前置问卷是否提前提示了后续访谈的研究内容，避免把受提示的回答误称为完全自发的认知。

## 质量标准

- **目标对齐**：核心问题有明确研究用途。
- **中立清晰**：不暗示答案，不把假设当成事实，一题一个回答重点。
- **人群适配**：根据实际经历分支，允许不知道、记不清或不适用。
- **可执行**：访谈时间合计正确，问卷选项合理，跳题有明确出口。
- **依据明确**：区分事实、假设、证据和解释，不夸大结论。
- **可检查**：审查覆盖题目，修改记录真实，未完成的测试明确标注。

筛选、事实确认和知情同意可以使用闭合式问题；不是所有题目都必须改成开放题。

## 使用示例

以生鲜 App 会员体验为例：

```text
请按本 Skill 设计中文访谈材料。

研究对象：叮咚买菜深圳用户，计划访谈8人，
覆盖在用会员、到期未续费用户和了解过但未开通用户。
研究目标：了解权益理解、开通决策、实际使用和续费或退出经历，
判断会员链路是否存在阻碍，探索优化方向。
执行条件：线上语音45分钟，征得同意后录音，安排查看App。
产出：访谈提纲，以及供这8人填写的访谈前背景问卷。

先检查缺失信息。不要编造当前权益或等级规则；
不要把这份背景问卷解释为定量验证。
请标记必问问题与可选追问，附时间安排、分支和审查记录。
```

预期产物包括研究简报、目标与题目映射、主持人提纲、背景问卷、研究者说明及问题检查记录。这是设计材料的使用示例，不代表已经获得真实用户研究结果，也不代表叮咚买菜官方项目。

## 已完成的测试与局限

开发过程中使用叮咚买菜案例完成了一轮独立 AI 生成测试，并对发现的问题修改规则、进行局部复测：

| 发现的问题 | 已补充的规则 |
| --- | --- |
| 前置背景表询问权益使用，后续却称为未提示回忆 | 联合检查提示效应，必要时将权益盘点后置 |
| 尚待确认的会员时长口径被笼统标为通过 | 区分通过、已修订、待确认和不适用 |
| 用户没有具体回忆时，信息来源追问缺少条件 | 仅对已提及内容追问来源，无内容则跳过 |

局部复测覆盖了背景表、权益认知模块及相关审查记录，不能视为所有场景完整回归测试通过。已完成基础文件结构与引用检查；标准 Python 校验器当时因缺少 YAML 依赖未完成运行。

尚未完成真实用户试访、问卷平台执行测试或多工具兼容性测试。正式使用前应朗读问题，进行小规模试访或预测试，核对耗时、措辞和跳题路径。

AI 审查不能保证零偏差；小样本访谈不能直接推算总体比例，用户表达的意愿也不能当作未来行为或转化效果。

## 输出格式与执行范围

默认可以直接输出文本或 Markdown。导出 Word、PDF 或在线表单，取决于所用 AI 工具是否具备对应能力，本项目本身不包含文档渲染器或表单发布程序。

设计材料不等于执行研究。联系受访者、发布问卷、录音和收集数据需要另行安排。公开分享材料时，请移除受访者个人信息、真实录音和不应公开的研究数据。
